# Phase 6.4: Unified Search Bar - Research

**Researched:** 2026-01-29
**Domain:** React component architecture, Google Places API, responsive design
**Confidence:** HIGH

## Summary

This phase merges the existing `KeywordSearch` and `LocationSearch` components into a single unified search bar component following Eventbrite's design pattern. The codebase already has all necessary infrastructure: `useIpLocation` for IP-based location, `useGoogleMaps` for Places API, `CitySearchInput` for autocomplete logic, `useIsMobile` for responsive detection, and both Sheet (Radix) and Drawer (Vaul) components for mobile modals.

The key technical challenge is configuring Google Places API to return only geographic regions (cities, countries, states) while filtering out postal codes and addresses. The existing `CitySearchInput` uses `types: ['(cities)']` which is correct but needs enhancement to support the "(regions)" concept (countries, states) while still excluding postal codes which are unfortunately included in the `(regions)` type collection.

**Primary recommendation:** Create a single `UnifiedSearchBar.tsx` component that renders inline on desktop and opens a Drawer modal on mobile. Use Google Places API with `types: ['(cities)']` and add client-side filtering to validate results by checking `addressComponents` for disallowed types.

**What:** Single component that renders differently based on screen size
**When to use:** When desktop inline layout should become mobile modal/drawer
**Example:**
```typescript

import { Drawer, DrawerContent, DrawerTrigger } from '@/components/ui/drawer';

export function UnifiedSearchBar() {
  const isMobile = useIsMobile();

  if (isMobile) {
    return (
      <Drawer>
        <DrawerTrigger asChild>
          <button>Search trigger for mobile</button>
        </DrawerTrigger>
        <DrawerContent>
          {/* Full search interface */}
        </DrawerContent>
      </Drawer>
    );
  }

  return (
    <div className="flex items-center border rounded-lg">
      {/* Inline desktop layout */}
    </div>
  );
}
```

### Anti-Patterns to Avoid
- **Multiple search hooks:** Don't create separate state for keyword and location. Use single `useEventFilters` as source of truth.
- **Duplicating IP location logic:** Don't re-implement IP detection. Reuse existing `useIpLocation` hook.
- **Synchronous location updates:** Don't update URL filters on every keystroke for location. Only update on explicit search button click.

## Common Pitfalls

### Pitfall 1: Google Places `(regions)` Includes Postal Codes
**What goes wrong:** Using `types: ['(regions)']` returns postal codes which user wants excluded
**Why it happens:** Google's `(regions)` collection includes `postal_code` type by design
**How to avoid:** Either use `types: ['(cities)']` only, OR use `(regions)` with client-side filtering
**Warning signs:** Users can select zip codes like "20121" and search by postal code

**Client-side validation approach:**
```typescript
// After fetching place details, check addressComponents
const isValidRegion = (addressComponents: AddressComponent[]) => {
  const types = addressComponents.flatMap(c => c.types);

  // Reject if primary type is postal_code, street_address, route, or premise
  const invalidTypes = ['postal_code', 'street_address', 'route', 'premise', 'subpremise'];
  const primaryType = addressComponents[0]?.types[0];

  return !invalidTypes.includes(primaryType);
};
```

### Pitfall 2: Debounce Strategy Mismatch
**What goes wrong:** Location search triggers API calls on every keystroke, or keyword search doesn't feel responsive
**Why it happens:** Keyword and location have different UX requirements
**How to avoid:**
- Keyword: 300ms debounce with immediate URL update (real-time filtering)
- Location: 350ms debounce for autocomplete suggestions (matches existing CitySearchInput)
**Warning signs:** Laggy keyword search, excessive Google API billing

### Pitfall 3: Location Display State Confusion
**What goes wrong:** Showing full address "Milano, Lombardia, Italia" instead of "Milano"
**Why it happens:** Using prediction.description directly instead of extracting city name
**How to avoid:** Extract city from addressComponents `locality` type, fallback to first part before comma
**Warning signs:** Cluttered location display, inconsistent formatting

### Pitfall 4: Mobile Drawer Input Focus
**What goes wrong:** Virtual keyboard doesn't appear when drawer opens on mobile
**Why it happens:** Focus not set to input after drawer animation completes
**How to avoid:** Use `autoFocus` on input or `onOpenAutoFocus` on DrawerContent
**Warning signs:** User has to tap input manually after opening search drawer

### Pitfall 5: Search Button State Management
**What goes wrong:** Search button triggers search even when no location is selected
**Why it happens:** Not tracking whether user has completed location selection
**How to avoid:** Track `pendingLocation` state separate from `confirmedLocation` in URL
**Warning signs:** Empty location searches, confusing UX where nothing happens on search

  for (const component of place.addressComponents) {
    if (component.types.includes('locality')) {
      cityName = component.longText;
      break;
    }
  }
  // Fallback to administrative_area_level_3 if locality not found

        break;

    }
  }

## Open Questions

Things that couldn't be fully resolved:

1. **Country/State Filtering**
   - What we know: `(cities)` returns only cities. User wants to allow searching by country, state, region too.
   - What's unclear: Do we need to support searching for "Italia" or "Lombardia" as locations?
   - Recommendation: Start with `(cities)` only. If user feedback requests broader regions, add client-side filtering on `(regions)` results to exclude postal codes.

2. **Location Display Truncation**
   - What we know: User wants "Milano" not "Milano, Italia"
   - What's unclear: What about ambiguous city names? "Paris, France" vs "Paris, Texas"?
   - Recommendation: Show city name only in the input. If disambiguation needed, could show country in a tooltip or smaller text below.

3. **Radius Selector Placement**
   - What we know: Current LocationSearch has inline radius selector. User didn't specify where it goes in unified bar.
   - What's unclear: Should radius be in unified search bar, or moved to UnifiedFilters?
   - Recommendation: Remove radius from unified search bar, keep it in UnifiedFilters. Unified bar focuses on keyword + location selection only.
