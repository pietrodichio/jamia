  <action>
Create `apps/backend/src/email-preferences/email-preferences.controller.spec.ts` following the same pattern established in plan 01 (createTestApp helper, guard override, ValidationPipe replication from main.ts).

**Mock service:** `mockEmailPreferencesService` with `jest.fn()` for: `getPreferences`, `updatePreferences`, `unsubscribeByToken`.

**Test suites:**

1. **GET /email-preferences (authenticated):**
   - Returns 200 with user's preferences. Passes user.id to getPreferences.

2. **PATCH /email-preferences (authenticated):**
   - Valid payload `{ digest_enabled: true, digest_frequency: 'weekly' }` returns 200.
   - Passes user.id and dto to updatePreferences.
   - Invalid `digest_frequency: 'hourly'` returns 400 with error on `digest_frequency` property.
   - Valid boolean-only update `{ digest_enabled: false }` returns 200 (frequency is optional).

3. **POST /email-preferences/unsubscribe/:token (public):**
   - Valid token returns 201 (NestJS @Post default) with `{ message: 'Unsubscribed successfully' }`.
   - Service throws NotFoundException for invalid token -> returns 404.

4. **GET /email-preferences/unsubscribe/:token (public):**
   - Valid token returns 200 with `{ message: 'Unsubscribed successfully' }`.
   - Invalid token -> 404.

5. **Unauthorized access:** Build app with `canActivate: () => false`. Verify `GET /email-preferences` returns 403. Verify `POST /email-preferences/unsubscribe/any-token` still works (public route should NOT be blocked -- note: this depends on how the @Public decorator interacts with the test guard override. If the test guard override blocks everything including @Public routes, skip this specific sub-test and document why).

**Important note about EmailPreferencesController:** The PATCH endpoint uses `@Body(new ValidationPipe({ transform: true }))` as a parameter-level pipe instead of relying on the global pipe. The global ValidationPipe should still work for the test since NestJS applies both parameter-level and global pipes. But test with both valid and invalid payloads to confirm validation fires.

  <action>
Create `apps/backend/src/profiles/profiles.controller.spec.ts` following the same pattern.

**Mock service:** `mockProfilesService` with `jest.fn()` for: `searchUsers`, `getPublicProfile`, `getProfile`, `updateProfile`.

**Test suites:**

1. **GET /profiles/search (authenticated):**
   - Returns 200 with search results. Passes query params (q, limit, jamId) to searchUsers.

2. **GET /profiles/public/:id (public):**
   - Returns 200 with public profile. Passes id to getPublicProfile.
   - Service throws NotFoundException for unknown id -> 404.

3. **GET /profiles/:id (authenticated):**
   - Returns 200 with profile. Passes id to getProfile.
   - Service throws NotFoundException -> 404.

4. **PATCH /profiles/:id (authenticated):**
   - Valid payload `{ first_name: 'Alice', main_role: 'base' }` returns 200. Service receives (id, user.id, dto).
   - Invalid `main_role: 'invalid'` returns 400 with error on `main_role` property.
   - Unknown fields are stripped (whitelist: true).
   - Service throws ForbiddenException (user tries to update another user's profile) -> 403.

**Important note about ProfilesController:** Like EmailPreferencesController, the PATCH endpoint uses `@Body(new ValidationPipe({ transform: true }))` as a parameter-level pipe. The global pipe may not apply its `exceptionFactory` for this endpoint. Test the validation behavior and if the error format differs from the global pipe format, document it in the test (the parameter-level pipe uses default NestJS error format, not the custom `Record<string, string>` format). Adjust assertions accordingly -- the 400 response body may have `message` array format instead of `{ property: error }` format.
