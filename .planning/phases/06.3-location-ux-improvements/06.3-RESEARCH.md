**Researched:** 2026-01-29

## Summary

This phase improves location detection UX for event discovery. The codebase already has solid foundations: `LocationSearch.tsx` implements geolocation with IP fallback (on button click), `useEventFilters.ts` manages location state via URL params, and `EventTypeStep.tsx` demonstrates Google Places autocomplete with 350ms debounce. The key gap is that location detection requires explicit user action - users must click a button to get their location rather than having a seamless initial experience.

The recommended approach is: (1) use IP-based location as immediate silent fallback on discovery page load with no user action required, (2) offer a "Use precise location" button that requests geolocation permission following Chrome's best practice of never auto-prompting, (3) add city/place search reusing existing Google Places autocomplete infrastructure, and (4) store search location in URL params (already implemented) without modifying profile.

**Primary recommendation:** IP fallback first (silent, no permission needed), GPS upgrade on explicit user action, city search via existing Google Maps integration.

### Pattern 1: Silent IP Location on Mount

**What:** Fetch IP-based location automatically when user visits discovery page without saved location.
**When to use:** First visit to /discover without lat/lng in URL params.
**Why:** No permission prompt needed, provides immediate value, unblocks discovery.

```typescript
// Source: Existing LocationSearch.tsx pattern + React Query
// useIpLocation.ts
export function useIpLocation() {
  return useQuery({
    queryKey: ['ip-location'],
    queryFn: async () => {
      const response = await fetch('https://ipapi.co/json/');
      if (!response.ok) throw new Error('IP location failed');
      const data = await response.json();
      return {
        lat: data.latitude,
        lng: data.longitude,
        city: data.city,
        isApproximate: true,
      };
    },
    staleTime: 5 * 60 * 1000, // 5 min cache
    gcTime: 30 * 60 * 1000, // 30 min garbage collection
    retry: 1, // Single retry on failure
  });
}
```

### Pattern 2: Geolocation Permission Query

**What:** Check geolocation permission state without prompting user.
**When to use:** To show appropriate UI (button text, icon) based on permission status.
**Why:** Avoid surprise permission prompts, enable smart UI adaptation.

```typescript
// Source: MDN Permissions API
// useGeolocationPermission.ts
export function useGeolocationPermission() {
  const [permission, setPermission] = useState<'granted' | 'denied' | 'prompt' | 'unsupported'>('prompt');

  useEffect(() => {
    if (!('permissions' in navigator)) {
      setPermission('unsupported');
      return;
    }

    navigator.permissions.query({ name: 'geolocation' }).then(result => {
      setPermission(result.state);
      result.onchange = () => setPermission(result.state);
    }).catch(() => {
      setPermission('unsupported'); // Safari fallback
    });
  }, []);

  return permission;
}
```

### Anti-Patterns to Avoid

- **Auto-prompting geolocation on page load:** Chrome penalizes this, users block it, breaks future attempts. Always require user action.
- **Modifying profile location from search:** Search is temporary/exploratory, profile is permanent/preference.
- **Storing search location in localStorage/sessionStorage:** URL params are already perfect - bookmarkable, shareable, clears naturally.

## Common Pitfalls

### Pitfall 1: Auto-Prompting Geolocation Permission

**What goes wrong:** Lighthouse fails audit, users block permission, Chrome may quiet-block future prompts entirely.
**Why it happens:** Developers assume "users want location" and prompt immediately.
**How to avoid:** Never call getCurrentPosition() without explicit user action (button click). Use IP location as silent default.
**Warning signs:** Geolocation code in useEffect without user trigger.

### Pitfall 2: Safari Permissions API Unsupported

**What goes wrong:** navigator.permissions.query throws, crashes permission detection.
**Why it happens:** Safari doesn't support Permissions API for geolocation.
**How to avoid:** Wrap in try/catch, fall back to 'unsupported' or 'prompt' state.
**Warning signs:** Unhandled promise rejection in Safari console.

### Pitfall 3: Mixing Search Location with Profile

**What goes wrong:** User explores Rome, their profile location changes from Milan to Rome permanently.
**Why it happens:** Reusing profile update logic for search.
**How to avoid:** Search location ONLY goes to URL params via updateFilter(). Profile location ONLY updates via profile API.
**Warning signs:** profilesApi calls in location search code.

### Pitfall 4: IP Location Rate Limiting

**What goes wrong:** ipapi.co blocks requests after 1000/day (free tier) or 30K/month.
**Why it happens:** Every page load triggers IP lookup.
**How to avoid:** Cache aggressively with React Query (5-30 min staleTime). Only fetch if no lat/lng in URL params.
**Warning signs:** 429 errors from ipapi.co in network tab.

### Pitfall 5: Empty State Without Guidance

**What goes wrong:** Users see "No events found" with no actionable path forward.
**Why it happens:** Empty state treated as dead end.
**How to avoid:** Always show why (no location? no results in area?) and what to do (set location, expand radius, try city search).
**Warning signs:** Generic "Nessun evento trovato" without context.

## Open Questions

Things that couldn't be fully resolved:

1. **IP Location Service Long-term**
   - What we know: ipapi.co currently used, 1000 free requests/day
   - What's unclear: Whether this limit will be sufficient at scale
   - Recommendation: Keep ipapi.co for now, monitor usage, have ip-api.com as backup (45/min rate limit, non-commercial only)

2. **City Search vs Full Address Search**
   - What we know: Can restrict to cities with `types: ['(cities)']`
   - What's unclear: Whether users want venue-level search in discovery (vs event creation)
   - Recommendation: Start with cities only for trip planning use case; full address search available in event creation already

3. **Location Indicator in Header vs Filter Bar**
   - What we know: Current location button is in filter bar
   - What's unclear: Best placement for "searching in [City]" indicator
   - Recommendation: Add subtle indicator near location controls showing current search context
