# Phase 12.1: Jam Management Regression Fix - Research

**Researched:** 2026-02-24
**Domain:** Bidirectional data synchronization, route unification, NestJS/Supabase architecture
**Confidence:** HIGH (codebase analysis, existing sync patterns verified)

---

## Summary

Phase 12.1 fixes a critical regression where the unified event creation wizard (`/create-event`) fails to create corresponding `jams` records when users create a "managed jam" (type="jam" with manageParticipants=true). This breaks participant management, communication features, and clone functionality that depend on the `jams` table.

The root cause is asymmetric data flow: the old `/create-jam` flow wrote to `jams` table first and synced to `events` via `eventsService.createEventFromJam()`. The new `/create-event` flow writes only to `events` table, with no reverse sync to create a `jams` record. The `/jam/:id` routes (JamDetailsLayout, JamOverviewPage, JamCommunicationPage) query the `jams` table directly via `jamsApi.getJamById()`, returning "Jam not found."

The fix requires: (1) bidirectional sync logic in `EventsService` to create `jams` records when `type='jam'` events with `manageParticipants=true` are created, (2) route unification so `/jam/:id` works for both legacy jams and event-based managed jams, and (3) ensuring clone/duplicate and dashboard navigation work correctly.

**Primary recommendation:** Implement reverse sync in `EventsService.createEvent()` and `EventsService.publishEvent()` to create corresponding `jams` records with a `source_event_id` foreign key, then update `JamsService` to accept lookups by either `jams.id` or `jams.source_event_id`.

## Architecture Patterns

### Current Data Flow (Broken)

```
Old Flow (Working):
/create-jam → JamsService.createJam() → INSERT jams → EventsService.createEventFromJam() → INSERT events
                                                       ↑
                                              (if managed + published)

New Flow (Broken):
/create-event → EventsService.createEvent() → INSERT events → [NO JAM CREATED]
                                                                    ↓
                                              /jam/:id → JamsService.getJamById() → "Jam not found"
```

### Fixed Data Flow

```
/create-event → EventsService.createEvent() → INSERT events
                                                     ↓
                              (if type='jam' AND manageParticipants=true)
                                                     ↓
                              EventsService.createJamFromEvent() → INSERT jams (with source_event_id)
                                                     ↓
/jam/:id → JamsService.getJamById() OR getJamBySourceEventId() → Jam found
```

### Pattern 1: Reverse Sync (Event → Jam)

**What:** Create a `jams` record when an event with `type='jam'` and participant management is created
**When to use:** When `EventsService.createEvent()` or `EventsService.publishEvent()` is called with `type='jam'` and jam management fields are populated

**Implementation approach:**
```typescript
// EventsService.createJamFromEvent() - new method
async createJamFromEvent(event: Event, userId: string): Promise<any> {
  // Only create jam for managed jams (manageParticipants = true implied by capacity being set)
  if (event.type !== 'jam') {
    return null;
  }

  const jamData = {
    owner_id: event.owner_id,
    name: event.title,
    location_text: event.location_text,
    location_lat: event.location_lat,
    location_lng: event.location_lng,
    gmaps_link: event.gmaps_link,
    starts_at: event.starts_at,
    ends_at: event.ends_at,
    description: event.description,
    status: event.status,
    source_event_id: event.id,  // New FK linking back to event
    // Jam-specific fields from event metadata or defaults
    capacity: event.capacity,
    auto_promote: event.auto_promote ?? true,
    public_participants: event.public_participants ?? true,
  };

  const { data, error } = await this.supabase
    .from('jams')
    .insert(jamData)
    .select()
    .single();

  if (error) {
    console.error('Failed to create jam from event:', error);
    return null;
  }

  return data;
}
```

### Pattern 2: Database Schema Addition

**What:** Add `source_event_id` column to `jams` table (mirrors existing `source_jam_id` in `events`)
**When to use:** Links jam records to their source event for bidirectional sync

```sql
-- Migration: Add source_event_id to jams table
ALTER TABLE jams
  ADD COLUMN source_event_id UUID REFERENCES events(id) ON DELETE CASCADE;

-- Create index for reverse lookup
CREATE INDEX idx_jams_source_event_id ON jams(source_event_id) WHERE source_event_id IS NOT NULL;

-- Unique constraint: one jam per event
CREATE UNIQUE INDEX idx_jams_source_event_unique ON jams(source_event_id) WHERE source_event_id IS NOT NULL;

COMMENT ON COLUMN jams.source_event_id IS 'Links jam to source event created via /create-event wizard. NULL for legacy jams.';
```

### Pattern 3: Jam Lookup Unification

**What:** Modify `JamsService.getJamById()` to handle lookup by event ID when jam not found by jam ID
**When to use:** When `/jam/:id` route is accessed with an event ID instead of jam ID

```typescript
// JamsService - modified getJamById()
async getJamById(jamIdOrEventId: string, userId?: string, isSuperAdmin = false) {
  // First, try direct lookup by jam ID
  let { data, error } = await this.supabase
    .from('jams')
    .select(`*, jam_participants (id, state)`)
    .eq('id', jamIdOrEventId)
    .single();

  // If not found, try lookup by source_event_id
  if (error && error.code === 'PGRST116') {  // Not found
    const result = await this.supabase
      .from('jams')
      .select(`*, jam_participants (id, state)`)
      .eq('source_event_id', jamIdOrEventId)
      .single();

    data = result.data;
    error = result.error;
  }

  if (error || !data) {
    throw new NotFoundException('Jam not found');
  }

  // ... rest of permission checks and return
}
```

### Pattern 4: Event Form Fields for Managed Jams

The `CreateEvent.tsx` form already includes fields for managed jams via `JamParticipantFields`:
- `manageParticipants` - boolean to enable participant management
- `capacity` - total capacity
- `desired_bases_min/max`, `desired_flyers_min/max` - role quotas
- `auto_promote` - auto-promote from waitlist
- `public_participants` - show participants publicly
- `visibility` - public vs private (share-by-link)

These fields need to be:
1. Passed to the backend in `CreateEventDto`
2. Stored on the event record (requires schema update)
3. Synced to the jam record during reverse sync

### Anti-Patterns to Avoid

- **Database triggers for sync:** User decision was application-level sync. Don't use Postgres triggers - harder to debug, version control, and maintain.
- **Dual writes from frontend:** Don't make the frontend call both events API and jams API. Keep sync logic in backend.
- **Breaking legacy flow:** The existing jams→events sync (via `createEventFromJam()`) must continue working for backward compatibility.
- **Redirecting /jam/:id to /events/:id:** This would lose participant management UI. The `/jam/:id` route must continue working.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| ID lookup fallback | Manual try/catch cascade | Single query with OR condition or two-phase lookup | More maintainable, clearer intent |
| Data transformation | Ad-hoc field mapping | Centralized mapping functions | Prevents drift between jam and event field names |
| Sync triggering | Manual sync calls scattered | Service method that handles all sync scenarios | Single source of truth for when sync happens |

**Key insight:** The existing `EventsService.createEventFromJam()` and `EventsService.syncJamUpdate()` patterns should be mirrored for reverse sync. Don't invent new patterns.

## Common Pitfalls

### Pitfall 1: Circular Sync Loop

**What goes wrong:** Event creates jam which creates event which creates jam...
**Why it happens:** Both `JamsService.createJam()` and `EventsService.createEvent()` have sync logic
**How to avoid:**
- Check for `source_event_id` before syncing jam→event (skip if already event-sourced)
- Check for `source_jam_id` before syncing event→jam (skip if already jam-sourced)
**Warning signs:** Infinite recursion, duplicate records with matching source FKs

### Pitfall 2: Inconsistent Status

**What goes wrong:** Event is published but linked jam is still draft
**Why it happens:** Status changes not propagated to linked record
**How to avoid:** Update `EventsService.publishEvent()` to also publish linked jam (if exists). Update `JamsService.publishJam()` to also publish linked event (if exists).
**Warning signs:** Jam shows as draft in `/jam/:id` but appears in public event listings

### Pitfall 3: Missing Jam Fields in Events Table

**What goes wrong:** Event created but reverse sync fails because jam-specific fields (capacity, auto_promote, etc.) aren't stored
**Why it happens:** `events` table doesn't have columns for jam management fields
**How to avoid:** Either:
1. Add jam management columns to `events` table (stores redundantly but enables reverse sync), OR
2. Pass jam-specific fields separately in a `jam_settings` JSON column, OR
3. Create jam immediately during event creation (before returning response)
**Warning signs:** Jams created from events have null/default capacity, auto_promote, etc.

### Pitfall 4: Route Parameter Ambiguity

**What goes wrong:** `/jam/:id` receives an event ID, but UI expects jam-specific data
**Why it happens:** Dashboard "Manage" links point to `/jam/${event.id}` instead of `/jam/${jam.id}`
**How to avoid:**
1. JamsService lookup accepts either ID type (preferred - see Pattern 3)
2. OR store jam.id on event record for correct linking
3. OR redirect from event ID to jam ID in JamDetailsLayout
**Warning signs:** "Jam not found" errors when clicking manage from dashboard

### Pitfall 5: Clone Functionality Breaks

**What goes wrong:** `jamsApi.cloneJam()` fails because the original is an event-based jam without a jams record
**Why it happens:** Clone looks up jam by ID, but ID is an event ID
**How to avoid:** Same fix as Pitfall 4 - lookup unification in JamsService
**Warning signs:** Clone button shows error or 404

### Example 2: Reverse Sync in EventsService.createEvent()

```typescript
// apps/backend/src/events/events.service.ts
async createEvent(ownerId: string, createEventDto: CreateEventDto) {
  // ... existing event creation logic ...

  const { data: event, error } = await this.supabase
    .from('events')
    .insert({
      owner_id: ownerId,
      ...restDto,
      ...locationFields,
      status: 'draft',
    })
    .select()
    .single();

  if (error) {
    throw new Error(`Failed to create event: ${error.message}`);
  }

  // REVERSE SYNC: Create corresponding jam for managed jams
  if (createEventDto.type === 'jam' && createEventDto.manage_participants) {
    await this.createJamFromEvent(event, createEventDto, ownerId);
  }

  await this.auditService.log(event.id, ownerId, 'event_created', {
    event_title: createEventDto.title,
    event_type: createEventDto.type,
  });

  return event;
}

private async createJamFromEvent(
  event: any,
  dto: CreateEventDto,
  userId: string
): Promise<any> {
  const jamData = {
    owner_id: event.owner_id,
    name: event.title,
    location_text: event.location_text,
    location_lat: event.location_lat,
    location_lng: event.location_lng,
    gmaps_link: event.gmaps_link,
    starts_at: event.starts_at,
    ends_at: event.ends_at,
    description: event.description,
    status: 'draft',
    source_event_id: event.id,
    // Jam-specific fields from DTO
    capacity: dto.capacity ?? null,
    desired_bases_min: dto.desired_bases_min ?? null,
    desired_bases_max: dto.desired_bases_max ?? null,
    desired_flyers_min: dto.desired_flyers_min ?? null,
    desired_flyers_max: dto.desired_flyers_max ?? null,
    auto_promote: dto.auto_promote ?? true,
    public_participants: dto.public_participants ?? true,
  };

  const { data: jam, error } = await this.supabase
    .from('jams')
    .insert(jamData)
    .select()
    .single();

  if (error) {
    console.error('Failed to create jam from event:', error);
    // Don't throw - event creation should succeed even if jam sync fails
    // Log for debugging but continue
    return null;
  }

  // Update event with source_jam_id for bidirectional linking
  await this.supabase
    .from('events')
    .update({ source_jam_id: jam.id })
    .eq('id', event.id);

  // Add owner as participant
  await this.supabase
    .from('jam_participants')
    .insert({
      jam_id: jam.id,
      user_id: userId,
      role: 'both',
      state: 'participant',
      source: 'owner',
    });

  return jam;
}
```

## Open Questions

1. **Where to store jam-specific fields for events?**
   - Options: (A) Add columns to `events` table, (B) Use JSON column on events, (C) Don't store - read from linked jam
   - Recommendation: Option A - add columns. Keeps sync simple and allows jam-specific fields on event detail pages.

2. **Should `/jam/:id` accept both jam ID and event ID?**
   - What we know: Users may have bookmarked event IDs or share event URLs
   - Recommendation: Yes - JamsService should handle both. Simpler than fixing all link sources.

3. **What happens to existing events created as jams without jam records?**
   - What we know: Any jam-type events created via `/create-event` before this fix have no jam record
   - Recommendation: Add a migration or admin script to create missing jam records for existing `type='jam'` events. Or handle gracefully in UI.

4. **Should we keep both `/create-jam` and `/create-event`?**
   - What we know: `/create-jam` currently redirects to `/create-event` (see App.tsx line 81)
   - Recommendation: Keep the redirect. No need to maintain two flows.
