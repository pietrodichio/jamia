## Summary

This phase reorganizes the existing Dashboard.tsx (543 lines) into two distinct sections: "Participations & Event Discovery" and "Event Management". The current dashboard already has a modular component architecture with StatisticsSection, UpcomingEventsSection, RecommendationsSection, and DashboardActions extracted into separate files.

The project already has Radix UI Tabs component available (`@radix-ui/react-tabs@1.1.12`) with a shadcn/ui wrapper at `src/components/ui/tabs.tsx`. This is the recommended approach for the two-section split due to accessibility features, existing project patterns, and the related content nature of both sections.

**Primary recommendation:** Use Radix UI Tabs with URL parameter synchronization (following existing `UnifiedEventView.tsx` pattern) for the two dashboard sections.

### Pattern 1: URL-Synchronized Tabs (Existing Project Pattern)
**What:** Active tab state stored in URL search params for bookmarkability
**When to use:** Dashboard sections users may want to directly link to
**Example:**
```typescript
// Source: Derived from existing UnifiedEventView.tsx pattern
import { useSearchParams } from 'react-router-dom';
import { Tabs, TabsList, TabsTrigger, TabsContent } from '@/components/ui/tabs';

type DashboardSection = 'participate' | 'manage';

export function DashboardTabs() {
  const [searchParams, setSearchParams] = useSearchParams();

  // Read section from URL, default to 'participate'
  const activeSection = (searchParams.get('section') || 'participate') as DashboardSection;

  const setSection = (section: DashboardSection) => {
    setSearchParams(
      (params) => {
        const newParams = new URLSearchParams(params);
        newParams.set('section', section);
        return newParams;
      },
      { replace: true }
    );
  };

  return (
    <Tabs value={activeSection} onValueChange={(v) => setSection(v as DashboardSection)}>
      <TabsList aria-label="Sezioni della dashboard">
        <TabsTrigger value="participate">
          <Users className="mr-2 h-4 w-4" />
          Partecipazioni
        </TabsTrigger>
        <TabsTrigger value="manage">
          <Calendar className="mr-2 h-4 w-4" />
          Gestione Eventi
        </TabsTrigger>
      </TabsList>
      <TabsContent value="participate">
        <ParticipationsTab userId={userId} />
      </TabsContent>
      <TabsContent value="manage">
        <EventManagementTab userId={userId} />
      </TabsContent>
    </Tabs>
  );
}
```

**What:** Each tab content as self-contained component with own data fetching
**When to use:** Separating concerns, lazy loading tab content

### Anti-Patterns to Avoid
- **Don't duplicate data fetching:** Both tabs need some shared data (user profile, auth state) - keep that in parent Dashboard.tsx
- **Don't render inactive tab content eagerly:** Radix Tabs only renders active tab by default - don't use forceMount
- **Don't split auth/redirect logic:** Keep auth checks and redirects in Dashboard.tsx, not in individual tabs
- **Don't break existing URLs:** `/dashboard` should still work - default to first tab

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Tab keyboard navigation | Custom key handlers | Radix Tabs | Arrow keys, Home/End, focus management built-in |
| Tab accessibility | Manual ARIA attributes | Radix Tabs | WAI-ARIA compliant out of box |
| URL state sync | Custom state + useEffect | useSearchParams | react-router-dom handles encoding, history |
| Active tab styling | Manual class toggling | `data-[state=active]` | Radix provides semantic data attributes |

**Key insight:** Radix UI Tabs handles the complex accessibility and keyboard navigation requirements automatically. The existing shadcn/ui wrapper in the project already has appropriate styling for active/inactive states.

## Common Pitfalls

### Pitfall 1: Breaking Existing Query Keys
**What goes wrong:** Refactoring components changes query key structure, causing stale/missing data
**Why it happens:** Moving queries between components without considering cache invalidation
**How to avoid:** Keep existing query keys intact; existing components use keys like `['jams', 'my']`, `['jams', 'participating']`, `['events', 'my-events', userId]`
**Warning signs:** Data not refreshing, duplicate network requests, cache misses

### Pitfall 2: Auth Redirect Loop
**What goes wrong:** Tab components include auth checks that conflict with parent Dashboard.tsx checks
**Why it happens:** Copying auth logic when extracting components
**How to avoid:** Auth/redirect logic stays ONLY in Dashboard.tsx; tab components assume valid auth state
**Warning signs:** Infinite redirects, flickering UI, multiple navigate() calls

### Pitfall 3: Losing Existing Functionality
**What goes wrong:** Legacy jam management features (clone, manage managers) stop working
**Why it happens:** Not fully understanding existing JamCard props and handlers
**How to avoid:** Map all existing functionality before refactoring:
- `handleClone()` mutation
- `handleManageManagers()` query invalidation
- `isOwnerOrManager()` / `isOwner()` permission checks
- Clone mutation with toast feedback
**Warning signs:** Buttons don't work, permissions broken, no feedback on actions

### Pitfall 4: Duplicate Statistics
**What goes wrong:** Statistics appear twice or show different numbers per tab
**Why it happens:** Unclear whether stats are shared or tab-specific
**How to avoid:** Based on phase description, StatisticsSection should appear once at top level (before tabs), showing aggregate stats. Individual tabs may have contextual stats (e.g., "Your participations: X")
**Warning signs:** Confusing UI, redundant data display

### Pitfall 5: Tab Content Flash on Navigation
**What goes wrong:** Content flashes/reloads when switching tabs
**Why it happens:** Unmounting component triggers refetch, React Query cache invalidated
**How to avoid:** Use staleTime effectively (existing components use 2-5 minutes); TabsContent only unmounts when switching tabs - cache should serve
**Warning signs:** Spinner on every tab switch, unnecessary network requests

1. **Statistics Placement**
   - What we know: StatisticsSection shows aggregate stats (events created, participants managed)
   - What's unclear: Should stats be shown once (shared) or per-tab (contextual)?
   - Recommendation: Show once above tabs for overview; consider adding contextual mini-stats within each tab header if needed

2. **Legacy Jam Section Retention**
   - What we know: Current Dashboard has "Legacy Jams Management" section marked "kept for backward compatibility"
   - What's unclear: Should this remain as separate section after refactor, or fold into Event Management tab?
   - Recommendation: Fold into Event Management tab; the "legacy" label suggests it's the same content just needing reorganization

3. **Mobile Responsiveness**
   - What we know: Tabs work on mobile but may need horizontal scroll for many tabs
   - What's unclear: Exact behavior needed for small screens
   - Recommendation: With only 2 tabs, standard responsive behavior should work; test on mobile during implementation
